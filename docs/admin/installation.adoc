= Installing arsnova

arsnova is deployed as a set of containers orchestrated with Docker Compose.
A release provides everything needed to run it:

* Docker Compose configuration for all services and their dependencies
* `particifyctl`, a helper script wrapping the Compose commands

These files are published with each
https://github.com/particify/arsnova-server/releases[release], so a production system does not need
a clone of the repository.
In the repository they live in `.docker/compose/production`.

== Requirements

=== Hardware

* CPU: 4 Cores or vCPU
* RAM: 8 GiB
* Storage: 10 GiB for Docker images and containers, additional storage for volumes containing user data depends on usage

=== Software

* Linux (see https://docs.docker.com/engine/install/#server for availability of official Docker packages)
* https://docs.docker.com/engine/install/[Docker Engine] >= 20.10 (older versions might work but are not tested for compatibility)
* https://docs.docker.com/compose/install/linux/[Docker Compose] >= 2.0

== Usage

=== Preparations

. link:https://github.com/particify/arsnova-server/releases[Download the latest release].
. Extract the archive and switch to the extracted directory.
. Run `./particifyctl` to list all available commands.

=== Directory layout

`particifyctl`:: The command you run.
`local.env`:: Your environment overrides.
`local.compose.yaml`:: Your Docker Compose overrides.
`core4-config/`:: core4's `application.yaml`.
`core-config/`:: The version 3 core's `application.yml`, if it was customised.
`tls/`:: Your certificates.
`provided/`:: What the release ships.

Everything but `provided/` is yours to edit.
`provided/` is replaced wholesale by the next release, so a change made there is lost on the next
update; override the setting in `local.env` or `local.compose.yaml` instead.
`particifyctl` additionally writes `.env`, `.compose.yaml`, `.version` and `apisix.yaml`, which are
generated and should not be edited either.

=== Running

. Run `./particifyctl run`. Append `-d` to run in detached mode for production.
. Run `./particifyctl compose down` stop and remove the containers.

=== Configuration

The default configuration can be adjusted via environment variables.
To persist the configuration, add those variable assignments to `local.env` (one assignment per line).

|=======
|Variable |Default value |Description
|PORT |80 |Port on which the gateway serves HTTP
|HTTPS_PORT |443 |Port on which the gateway serves HTTPS, if certificates are configured
|JWT_SECRET |generated |Encryption token for authentication, shared by every service; generated into `local.env` when it is unset
|CHALLENGE_SECRET |generated |Token for the registration challenge, generated into `local.env` when it is unset
|JWT_DOMAIN |example.com |A domain usable as server ID (used for the JWT issuer/audience claim)
|ARSNOVA_HOSTNAME |localhost |Hostname for the application
|COMPOSE_PROFILES | |Set to `v3-migration` to start the version 3 services a data migration reads
|LEGACY_POSTGRESQL_TAG | |Version (Docker) tag for the PostgreSQL databases of the v3 services; required only with the `v3-migration` profile
|WEBSOCKET_TAG |latest |Version (Docker) for the WebSocket service
|AUTHZ_TAG |latest |Version (Docker) for the authz service, which only a version 3 migration starts
|CORE_TAG |latest |Version (Docker) for the v3 core service
|CORE4_TAG |latest |Version (Docker) for the core4 service
|COMMENTS_TAG |latest |Version (Docker) for comments service, which only a version 3 migration starts
|WEBCLIENT_TAG |latest |Version (Docker) for the webclient
|FORMATTING_TAG |latest |Version (Docker) for the formatting service
|COUCHDB_TAG |latest |Version (Docker) for CouchDB
|RABBITMQ_TAG |latest |Version (Docker) for RabbitMQ
|=======

Mail is configured by `core4` rather than through the environment, so the `MAIL_*` variables of
earlier versions no longer apply.
See <<Configuration file>>.

Example: `PORT=8100 ./particifyctl run`

=== Configuration file

Some settings cannot be expressed as environment variables, because Spring's relaxed binding cannot
recover a UUID's hyphens or a camelCase key from a variable name.
LDAP and SAML registrations and the `ui.*` settings are therefore configured in
`core4-config/application.yaml`, which is mounted into the `core4` container.

`core4` requires `mail.sender-address`, `mail.sender-name` and `service.root-url`, none of which
have a default, so that file has to exist before the service will start.
`particifyctl` warns when it is missing.

`security.jwt.secret` and `security.challenge.secret` are required as well but are not configured
there.
`update-config` generates `JWT_SECRET` and `CHALLENGE_SECRET` into `local.env` whenever they are
unset, so a new installation starts without anyone having to invent a value.
Only the first is worth keeping a copy of: every service reads it, and replacing it invalidates
every token they have issued.

Environment variables take precedence over the file, so `JWT_SECRET`, `JWT_DOMAIN` and
`CHALLENGE_SECRET` stay in `local.env`; setting the corresponding properties in the file would have
no effect.

The v3 core, which still runs alongside `core4`, reads `core-config/application.yml` in the same
way.
It is only needed for an installation which had a customised v3 configuration file.

See link:../development/ldap.adoc[the LDAP documentation] and
link:upgrading-to-v4.adoc[the upgrade guide] for the property structure.

=== Gateway

`./particifyctl update-gateway` generates the gateway's `apisix.yaml` from
`provided/apisix-routes.yaml`, the certificates in `tls/`, and `ARSNOVA_HOSTNAME_ALIASES` and
`CSP_FRAME_ANCESTORS`.
Run it, followed by `./particifyctl update-config`, after changing any of those.
The gateway picks the generated file up without a restart.

==== HTTPS

The gateway can terminate TLS.
Put `<hostname>_key.pem` and `<hostname>_cer.pem` into `tls/`, plus an optional `<hostname>_ca.pem`
chain, then run `./particifyctl update-gateway` followed by `./particifyctl update-config`.

The certificates are inlined into the gateway's configuration, because it cannot load them from a
path, so `update-gateway` has to be run again after each renewal.
Without certificates the gateway serves plain HTTP only.
With them, a plaintext request is redirected to HTTPS: `301` for `GET` and `HEAD`, `308` otherwise,
so a request keeps its method and body.
The redirect names no port, so an installation which publishes HTTPS somewhere other than 443 needs
whatever terminates TLS in front of the gateway to handle it.

==== Hostname aliases

`ARSNOVA_HOSTNAME_ALIASES` is a space-separated list of further names the installation answers on.
Each of them is redirected to `ARSNOVA_HOSTNAME` with a `301`.
The gateway matches no `Host` header of its own accord, so a name left out of this list serves the
application under itself rather than redirecting.

An alias reached over HTTPS also needs a certificate which covers it.
The aliases are added to the canonical hostname's certificate entry rather than getting one of their
own, so that certificate has to name them too -- otherwise the browser warns before it ever sees the
redirect.

==== Framing

`CSP_FRAME_ANCESTORS` is a space-separated list of origins allowed to embed the application in a
frame, sent as the `frame-ancestors` directive of a `Content-Security-Policy` header.
Left empty, no such header is sent at all and any origin may embed the application.
An installation which embeds the application in a learning management system over LTI has to list
that system's origins, or the launch is blocked.

=== Docker Compose overrides

If you need to override the default Docker Compose configuration, you can add your configuration in `local.compose.yaml`.
The local configuration takes precedence over the other `*.compose.yaml` files a release provides.
We recommend that you only use the `local.*` files to adjust the configuration, so you do not need to manually merge changes when updating.

== Upgrading from version 3

See link:upgrading-to-v4.adoc[].
Read it before starting: an upgraded installation needs its legacy databases pinned to the
PostgreSQL version they actually hold, and skipping that step makes PostgreSQL initialise an empty
cluster beside the existing data without reporting an error.

=== Version 3 services

A version 4 installation does not run the version 3 authorization and Q&A services or their
databases.
They are needed once, by the data migration, which reads room memberships from the authorization
service and the Q&A data straight out of its database.

Set `COMPOSE_PROFILES=v3-migration` in `local.env` to start them, and remove it once the migration
has completed.
Left running, the authorization service goes on mirroring room events into a database nothing reads.
A clean installation never needs the setting at all.

=== PostgreSQL updates

`LEGACY_POSTGRESQL_TAG` pins the PostgreSQL version of the v3 services' databases.
Those are the only images it governs and the `v3-migration` profile is the only thing which starts
them, so an installation which never held version 3 data never needs it.
Where the profile is set, `update-config` refuses to generate a configuration while the tag is not,
because an image reference of `postgres:` with nothing after the colon is only rejected once the
image is pulled.
Set it to the version the volumes actually hold - nothing derives it for you, and a wrong value
makes PostgreSQL create an empty cluster beside the existing data:

[source,shell]
----
docker run --rm -v particify_postgresql_data_auth:/d:ro alpine cat /d/PG_VERSION
----

Raising it to a new major version does not migrate the data.
PostgreSQL will not read a cluster created by an older version, and from version 18 it also expects
a different directory layout on the volume, so the data has to be converted first.

**Back up the volumes before converting.**
There is no rollback.

To convert, set `COMPOSE_PROFILES=v3-migration` so the databases start at all, override the image
for both in `local.compose.yaml`, and let them start once:

[source,yaml]
----
services:
  postgresql-authz:
    image: pgautoupgrade/pgautoupgrade:18-alpine
  postgresql-comments:
    image: pgautoupgrade/pgautoupgrade:18-alpine
----

That image detects an existing cluster of an older version and upgrades it in place, adjusting the
directory layout on the volume as needed.
Remove any mount override for these services at the same time, so the volume is mounted where the
current configuration expects it.

Once the services are up and the data is intact, drop the image override again and set
`LEGACY_POSTGRESQL_TAG` to the version that was migrated to.

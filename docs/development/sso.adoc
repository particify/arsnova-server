= Single Sign On

SAML is available as a login provider.
Every configured registration is advertised through `GET /api/configuration` and rendered as an
additional SSO provider on the login screen.
A login is started at `/api/saml2/authenticate/{registrationId}`,
and the service provider metadata is served at
`/api/saml2/service-provider-metadata/{registrationId}`.
A session started through SSO always carries the short lifetime and cannot ask to be remembered.
It also ends after `security.login.external-session-max-age` however actively it is used until then,
because the identity provider does not tell us when it revokes an account.
An identity provider which bounds the session itself, through `SessionNotOnOrAfter` of the
assertion's authentication statement, ends it earlier where that bound is the earlier one.
The assertion's own `NotOnOrAfter` is not read for this:
it limits how long the assertion may be replayed rather than how long the session lasts.
link:authentication.adoc[] covers the tokens themselves.

Users are authenticated by the identity provider.
On the first successful login, an account is created and linked to the registration through an
external login, keyed by the asserted ID attribute.
Every later login updates the account from the asserted attributes.

== Configuration

Registrations are keyed by a UUID, which is also the provider ID the account's external login is
stored under.
An empty map -- the default -- disables SAML, so nothing has to be configured to keep it off.

[source,yaml]
----
security:
  saml2:
    relyingparty:
      registration:
        fc62cd95-bea9-4aa3-987d-fa976ef300f3:
          entity-id: https://example.com/api/saml2/service-provider-metadata/{registrationId}
          username-mapping: MAIL_ADDRESS
          attribute-mapping:
            mail-address: urn:oid:0.9.2342.19200300.100.1.3
          signing:
            credentials:
              - private-key-location: file:credentials/rp.key
                certificate-location: file:credentials/rp.crt
          assertingparty:
            metadata-uri: https://idp.example.com/metadata
          metadata-verification:
            credentials:
              - certificate-location: file:credentials/federation-metadata-signing.crt
----

`entity-id`:: Entity ID of the service provider.
  `{registrationId}` is substituted with the registration's UUID.
`assertingparty.metadata-uri`:: Location of the identity provider's metadata.
  Required.
  It is fetched while the application starts and re-read afterwards, see below.
`assertingparty.entity-id`:: Entity ID of the identity provider.
  Only needed when the metadata describes more than one, see below.
`metadata-verification.credentials`:: Certificates the metadata document's own signature is
  verified against.
  Optional;
  unset accepts the document as read, see below.
`signing.credentials`:: Key and certificate used to sign requests.
  Signing is mandatory, so both locations have to be set;
  a registration missing either of them fails at startup.
`attribute-mapping`:: Names of the asserted attributes read into the account, see below.
`username-mapping`:: Whether the username is the mapped ID or the mail address, see below.
  `MAIL_ADDRESS` by default.
`title`:: Name shown to users selecting this registration on the login page.
  `SAML` by default, which leaves several registrations indistinguishable,
  so an installation offering more than one should set it.
`order`:: Position among the login options, `0` by default.

== Metadata refresh

The identity provider's metadata is fetched while the application starts and re-read on a schedule
after that, so a rotated signing key is picked up without a restart.

The schedule comes from the document itself:
the next refresh is due after three quarters of the time left until its `cacheDuration` or
`validUntil` runs out, clamped to at least 5 minutes and at most 4 hours.
A document which states neither is re-read every 4 hours.
None of this is configurable.
Over HTTP the request is conditional, so a document which has not changed costs a `304` and
nothing else.

A refresh which fails -- the identity provider is unreachable, answers with an error,
or serves something which does not parse -- is logged at `ERROR`,
and the last document which did parse stays in use.
Logins therefore survive an outage of the metadata endpoint.

What the fetch during startup does depends on where the metadata comes from.
A `file:` or `classpath:` source which cannot be read stops the application:
a path which does not resolve is a misconfiguration, and no retry will ever fix it.
An `http` or `https` source only logs at `ERROR`, and the application starts without it --
whether it could not be fetched at all, or was fetched and then rejected because it does not
parse or fails the signature verification below.
An endpoint serving an error page while it is itself being deployed looks no different from one
which is permanently misconfigured, so both are retried rather than either being fatal.
Every other login method -- local accounts, LDAP, and the other SAML registrations -- is
unaffected.

A registration left in that state authenticates nobody until a refresh succeeds.
It does not fall back to anything:
with no document there is no signing certificate to verify an assertion against,
so there is nothing it could safely accept.
Recovery needs no intervention, because the retry is the ordinary refresh:
the next attempt is due after the minimum delay of 5 minutes, and repeats until it succeeds.
The registration itself is logged once at `ERROR` when it becomes unusable and once at `INFO`
when it recovers, rather than on every lookup.

Metadata which describes more than one identity provider -- a federation aggregate -- needs
`assertingparty.entity-id` to settle which one the registration binds to.
Without it, metadata describing exactly one identity provider binds to that one,
and metadata describing several fails at startup with a message listing them.

=== Signature verification

`metadata-verification.credentials` pins the certificates the metadata document's own signature is
verified against.
It is optional and unset by default, so a document is accepted unverified unless certificates are
configured.
A registration with an `http` or `https` metadata location and no pinned certificate is logged at
`WARN` while the application starts, because the document's integrity then rests on the transport
alone.
A `file:` or `classpath:` location is trusted as read and is not warned about:
it comes from the deployment itself rather than across a network.

Verification is distinct from `assertingparty.verification.credentials`,
which pins the certificates that verify *assertions*.
A federation signs the aggregate it publishes with its operator's key,
not with the key of any identity provider described in it,
and the two rotate on unrelated cadences.

Once certificates are pinned, the document's root element has to be signed;
a document carrying no signature over its root is rejected, so a signature cannot simply be
stripped.
The signing certificate travels inside the document's own signature, and pinning is what makes
checking it worth anything: the key is taken from the document and then has to match one of the
configured certificates.

The property is a list, and that is how a rotation is carried.
When the federation announces its incoming metadata signing certificate, add it alongside the one
in use;
a signature matching any configured certificate is accepted, so both work throughout the announced
overlap window.
Remove the outgoing certificate once that window has passed.
A configured certificate within 90 days of its expiry is logged at `WARN` while the application
starts, because a missed rotation degrades quietly:
the refresh fails, the last good document keeps being served, and logins go on working while the
metadata silently stops moving.

== Attribute mapping

Each entry names the asserted attribute a profile field is read from.
The defaults are the SAML 2.0 subject ID and the LDAP-derived OIDs for mail address, given name and
surname.

`id`:: Attribute holding the ID which identifies the user to us.
  `urn:oasis:names:tc:SAML:attribute:subject-id` by default.
  A login fails if it is missing, because there is nothing left to key the account on.
`mail-address`:: Mail address, `urn:oid:0.9.2342.19200300.100.1.3` by default.
`given-name`:: Given name, `urn:oid:2.5.4.42` by default.
`surname`:: Surname, `urn:oid:2.5.4.4` by default.

The mail address is lowercased and has to be unique,
so it is not imported if another account already uses it.
That does not fail the login;
the account simply carries no mail address.
An assertion which carries no mail address at all leaves a stored one unchanged,
so an identity provider which stops releasing the attribute does not clear the address of every
account logging in afterwards.
The other side of that is deliberate:
an address the identity provider removes on purpose does not propagate here either.
The given name and surname follow the same rule:
an assertion which does not carry them leaves the stored values alone.

== Identity model

The account's username is what makes it verified, and it is also its public display ID -- the
identifier another user enters to share a room.
It is not a credential: a SAML user is always located through their external login,
never through the username.

`username-mapping` decides where it comes from:

`ID`:: The value of the `id` attribute, lowercased.
  Correct when that attribute is something a person recognises, such as a login name or a scoped
  identifier.
`MAIL_ADDRESS`:: The mail address, which is the default.
  Correct when the ID attribute is an opaque pairwise identifier, which no one could be expected to
  type.

Since the mail address is also what a local account's username is derived from, `MAIL_ADDRESS` puts
SAML and local accounts into one namespace on purpose.

Two consequences follow, and neither of them fails the login:
a username which is already in use leaves the account unverified,
and so does a mapping whose value is not available at all --
`MAIL_ADDRESS` with an identity provider which does not release the mail attribute.
An account left unverified this way is given a username by the next login which finds one free.

There is deliberately no such option for LDAP.
A directory always has a dedicated user ID attribute, and which attribute that is can already be
configured, so the choice a SAML deployment has to make does not arise there.
See link:ldap.adoc[].

== Development environment

=== Credentials

Signing of SAML requests is set up to be mandatory, so private and public keys need to be provided.
A second keypair belongs to the identity provider, which signs its realm metadata with it.
We do not store credentials in the repository -- even if they are only used for local development
purposes.
Instead, they can be generated after cloning the repository using the
link:core4/generate-credentials.sh[] script.
This script also creates realm data for Keycloak from a template,
substituting both certificates and the identity provider's private key into it.

Re-running it is safe: existing keypairs are kept and only the realm data is rendered again,
so a changed template can be picked up without invalidating the certificates an already imported
realm holds.
Pass `--force` to replace the keypairs instead -- the realm then has to be dropped as well,
see below.

=== Keycloak

The development environment includes Keycloak to help with the development of SSO features.
A realm configuration is included and automatically imported at startup.
The Keycloak service can be accessed at http://localhost:8080 (username: `admin`,
password: `admin`).

The realm ships two users which can log in through SSO, `saml-owner` and `saml-participant`,
each with a verified mail address at `example.com` and a password equal to its username.
Further users can be created by hand;
such a user needs a mail address which is marked as verified, and a password.

The realm signs its SAML metadata descriptor.
The signing keypair is generated by the credential script rather than by Keycloak at import time,
which is what makes its certificate pinnable:
a key which Keycloak generates changes whenever the realm is imported again.
The descriptor also publishes a `cacheDuration` of 10 minutes.

Keycloak signs the descriptor with the realm's own signing key,
so the development environment pins the same certificate which the descriptor's `KeyDescriptor`
publishes.
That is realistic for a single identity provider.
It does not reproduce a federation, whose aggregate is signed with a separate long-lived key
belonging to the federation operator.

core4's development configuration pins that certificate, the generated `idp.crt`,
as the metadata verification certificate,
so the development environment verifies the descriptor's signature rather than accepting it
unverified.
The credential script therefore has to have run before core4 starts:
the certificate is a required file now, the same way the service provider's key already was.

The import creates the realm only if it does not exist yet:
the strategy is `IGNORE_EXISTING`, and an existing realm is logged as
`Realm 'dev' already exists. Import skipped`.
Changes to the template therefore do not reach an environment which imported the realm already,
the users above included.
Deleting the realm makes the next start import it from the template again:

[source,shell]
----
./pdk compose exec keycloak /opt/keycloak/bin/kcadm.sh delete realms/dev --no-config \
  --server http://localhost:8080 --realm master --user admin --password admin
./pdk compose restart keycloak
----

If that does not work, resetting Keycloak's database has the same effect:

[source,shell]
----
./pdk compose stop keycloak
./pdk compose exec postgresql-keycloak psql -U keycloak -d postgres -c 'DROP DATABASE keycloak'
./pdk compose exec postgresql-keycloak psql -U keycloak -d postgres \
  -c 'CREATE DATABASE keycloak OWNER keycloak'
./pdk compose start keycloak
----

Removing Keycloak's database volume works as well.
Its name carries a Compose project prefix which differs per workspace,
so it should be looked up with `volume ls` rather than assumed.

Credentials are affected by the same behaviour:
regenerating them without dropping the realm leaves the realm holding the old signing certificate
while core4 signs with the new key, and Keycloak rejects every request.

=== Exercising metadata refresh and verification

The refresh interval is derived from the descriptor's `cacheDuration` and clamped to at least five
minutes, so the ten minutes the realm publishes result in a refresh roughly every seven and a half
minutes.
OpenSAML logs each refresh at `INFO`, naming the time the next one is due,
so nothing needs to be configured to see that refreshes happen.

`LOGGING_LEVEL_ORG_OPENSAML_SAML_METADATA_RESOLVER_IMPL=DEBUG` adds detail for each refresh,
but that detail is weak evidence here:
Keycloak sends neither `ETag` nor `Last-Modified` and stamps a fresh document ID onto every
response, so this identity provider never gives the conditional request a condition it can satisfy
and no refresh can end in a `304`.
Every refresh is reported as new metadata, whether anything actually changed or not.

What does prove a refresh took effect is changing the descriptor.
Adding a second RSA signing key provider to the realm in the admin console changes what the
descriptor advertises, and core4 picks that up within one refresh interval, without being restarted.
Which change it is depends on the priority given to the new provider:

* A *higher* priority than the seeded provider has Keycloak sign the descriptor with a key which is
  not pinned, so verification fails and the refresh is logged at `ERROR`.
  The last document which verified stays in use, so logins keep working until core4 is restarted.
* A *lower* priority leaves the signature valid and simply adds a second signing key to the
  descriptor.

Take care with the admin console while doing this:
saving the realm's general settings can write an empty signature algorithm back,
which switches descriptor signing off with nothing said about it.

== Migration from v3

link:v3-migration.adoc[] covers the migration itself:
the provider mapping a registration has to be paired with, how usernames and mail addresses are
settled, and what happens to an account which shares its address with a local one.

One thing is specific to SAML.
v3 had one installation-wide `security.user-display-id-attribute`, with the values `loginId` and
`mail` and `loginId` as its default.
`username-mapping` replaces it per registration, and its default is the other one --
so a v3 installation migrating with default configuration needs `username-mapping: ID` to keep the
display IDs its users know.
The v3 value the migration carries over is `loginId`,
which for SAML was the value of v3's own `user-id-attribute`, not the mail address.

== Limitations

* A UUID-keyed registration map cannot be configured through flat environment variables, because
  Spring's relaxed binding cannot recover the UUID's hyphens from an environment variable name.
  The production Compose stack configures core4 exclusively that way, so SAML cannot be set up there
  yet.
  LDAP shares this gap, and closing it is a task of its own.

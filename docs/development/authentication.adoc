All API endpoints, except for the challenge endpoint, require authentication.
In most cases, authentication for an existing user account is needed.
But for a few endpoints, a user account or respective authentication is not available, e.g. login or account creation.
For these cases, anonymous authentication is available, which does not authenticate a specific user.
It instead testifies that the client has solved a proof of work challenge.

== Proof of work

Proof of work is a method where the client has to solve a server provided cryptographic challenge.
While it is easy for the server to generate the challenge and verify the solution, it is expansive to solve for the client.
We use PoW as a form of protection against DoS attacks and bots.

For the implementation of a PoW algorithm the Altcha library is used.
The client fetches a challenge via `GET` request to `/api/challenge` and sends its solution to the URI as `POST` request.
If the challenge is verified successfully, the server responds with an authentication token.
This token has a short expiration time and is only accepted to authenticate a single request.

A solution posted with `"reusable": true` is exchanged for a reusable token instead,
which lets a client without a session use a few queries for a limited time.
It is valid for any number of requests until it expires,
after `security.challenge.reusable-token-validity` (5 minutes by default),
but authenticates only GraphQL requests over HTTP.
It grants only the role `CHALLENGE_SOLVED_REUSABLE`,
so it reaches only the operations whose authorization allows that role explicitly,
apart from introspection, which any authenticated request can use.
It belongs to no account, so permission checks on domain objects deny it.
It is signed with a key derived from the JWT secret for reusable tokens,
so no other service accepts it as a session,
and issuing it consumes the challenge, so one solution yields exactly one token.

The password strength check is the one use so far:
the `userPasswordStrength` query allows the reusable token's role,
and its default validity of 5 minutes covers typing a password (see <<password-strength>>).
Creating a guest session for such clients was rejected:
every visit to a password reset or invitation page would create a guest account
and switch the client into a guest login in the middle of the flow.

== Login throttling

`POST /api/auth/login` is rate limited per submitted username.
Attempts are counted before the credentials are checked and discarded again after a successful
login, so only failures accumulate.

Without a limit of our own, how many passwords a client may try is bounded only by the proof of work
challenge in front of the endpoint.
That challenge puts a cost on every attempt, but the resulting rate follows from how quickly the
client solves one, which is a property of its hardware rather than a bound we set.

The exposure is worst against an external directory (see link:ldap.adoc[]),
where repeated failures usually lock the account, but it is not specific to any one provider.

`security.login.attempt-limit`:: Attempts allowed per window, `20` by default.
`security.login.attempt-window`:: Length of the window, `2m` by default.

The counters are held in memory, so the limit applies per instance rather than across a deployment
with several replicas.

== Tokens

JSON Web Tokens are used to authentication clients statelessly for use of the API.
Following a common security practise, two separate tokens are used:

* A short-lived access token which authorizes the client for API access.
  It cannot be revoked.
  The client sends this token in the `Authorization` header for further API requests.
* A refresh token which allows the client to request new access tokens.
  It can be revoked by increasing the users token version.
  To protect this token against XSS attacks, it is stored using an `HttpOnly` cookie.
  Therefore, it is not accessible through JavaScript.
  It lives as long as the session it belongs to, see <<Session lifetime>>.

=== Session lifetime

A session lasts three hours, counted from its last refresh: each rotation of the refresh token
extends it by that period again, so a session ends three hours after the client stopped using it.

`POST /api/auth/login` accepts a `rememberMe` field to start a session lasting
`security.login.remember-me-max-age` instead, `180d` by default.
Only a login with a username and a password offers that choice;
a session started through an external login always carries the short lifetime.
A guest account is the exception: it exists as its refresh token alone,
so ending its session would discard the account with it, and it therefore always gets the
configured lifetime.

Leaving `security.login.remember-me-max-age` unset withdraws the option altogether.
`rememberMe` is then ignored, `GET /api/configuration` omits the `rememberMeEnabled` UI setting so
that a client hides the choice, and every session, a guest account's included,
is limited to three hours.

The lifetime travels as a claim of the signed refresh token, so a rotation continues the session
rather than deciding it anew.
A token issued before that claim existed keeps the remembered lifetime,
which is what it had been issued with.

A session resting on an external login ends after `security.login.external-session-max-age`, `30d` by
default, counted from the login rather than from its last refresh.
The account behind such a session is owned by whichever system authenticated it,
and that system does not tell us when it revokes one,
so ending the session and repeating the login is what asks it again.
A local account never carries a deadline:
this application is the authority for it, so nothing about it can be revoked elsewhere.

A system which ends the session itself is taken at its word where it is stricter than we are.
The session then ends at whichever bound comes first, so such a system can shorten the configured
period but never extend it, and an unset period withholds a bound of ours rather than discarding
the one we were given.
Only a bound on the session counts.
An assertion's own validity is not one -- it limits how long the assertion may be replayed, which
is a matter of minutes -- so it is deliberately left unread.
A session is therefore unbounded only where neither a period is configured nor a bound asserted.

The deadline travels as a second claim and a rotation does not move it along.
It shortens the last period of a session so that the refresh token expires with the session, and a
refresh arriving afterwards is rejected;
the decoder tolerates some clock skew, so the token alone would still be accepted for a moment.

So a refresh token carries two times which are not its own.
The `extendBy` claim is the idle period the session is granted again at every rotation, and the
`extendUntil` claim the instant it ends regardless of use;
the token itself expires at whichever of the two comes first.
Until the last token of a bounded session the period and the expiry agree,
which is what makes the claim look like a restatement of `exp - iat`.
It is not one, and reading it that way would be a defect:
a rotation which derived the period from a token already shortened by the deadline would take the
remainder for the session's period and hand out nothing longer ever again,
so a session refreshed once near its end would stay as brief as that one refresh left it.

== Local accounts

A local account authenticates with a username and a password, the username being the mail address
its owner verified.
Creating one is not a single request: the client first obtains a guest account
(`POST /api/auth/guest-account`), then claims it with the `claimUnverifiedUser` mutation, which
parks the address until the code sent to it is submitted.
An account can also be created for someone else, by an administrator through `adminCreateUser` or
by a room's owner through `grantRoomRoleByInvitation` -- both send an invitation and go through the
same service.

Two settings decide what is available:

`security.local-account.enabled`:: Whether local accounts exist at all, `true` by default.
`security.local-account.self-registration-enabled`:: Whether an account can be created by whoever
wants one, `true` by default.
Ignored while local accounts are disabled.

[cols="2,1,1"]
|===
|Path |`enabled: false` |`self-registration-enabled: false`

|`POST /api/auth/login` without a `providerId` |refused |unaffected
|`user-db` entry in `GET /api/configuration` |omitted |unaffected
|`claimUnverifiedUser` |refused |refused
|`grantRoomRoleByInvitation` for an address with no account |refused |refused
|`requestUserPasswordReset`, `resetUserPassword` |refused |unaffected
|`updateUserMailAddress` |refused |unaffected
|`adminCreateUser`, `adminVerifyUserById` |unaffected |unaffected
|===

Three of those paths carry a second check which neither column covers: `claimUnverifiedUser`,
`grantRoomRoleByInvitation` and `updateUserMailAddress` test the address against the allowed
domains below once a request gets past the settings above.
A verification already in flight is unaffected by either setting, since completing one finishes an
account rather than creating it.

Administrative actions are never gated, so an administrator creates and verifies accounts whatever
the settings say.
That is decided from the account acting rather than from the mutation called, which is why the
invitation is refused for a room owner and allowed for an administrator although both reach the
same service method.

A refusal is a domain exception rather than a denied `@PreAuthorize`, because the client cannot
explain the opaque `FORBIDDEN` that GraphQL turns an authorization denial into.

`security.local-account.allowed-mail-address-domains` restricts which addresses an account may be
created for, and is empty by default.
Each entry is a domain in which a `*` label matches exactly one label of the address' domain, so
`*.example.com` covers `mail.example.com` but not `example.com`.
The entries are checked and compiled while the application starts: a pattern which cannot match
locks out everyone it was meant to serve, and reporting that as an error about the submitted
address hides the actual mistake.
Changing one's own address is checked against the list as well, since a restriction one can leave
right after registering is no restriction.
So is an invitation, which would otherwise let a room's owner create the account the restriction
denies its holder -- unless an administrator sends it, administrative account creation being
ungated here as everywhere else.

=== Password strength

New passwords are checked against an estimate of how many guesses an attacker needs
(zxcvbn, via zxcvbn4j),
not against composition rules.
Composition rules accept predictable patterns like `P@ssw0rd`
while rejecting strong passwords without special characters,
and NIST SP 800-63B and OWASP ASVS advise against them.
Every operation that sets a password checks it:
`claimUnverifiedUser`, `verifyUserMailAddressUnauthenticated`, `resetUserPassword` and
`updateUserPassword` reject a weak one with `extensions.code` `WEAK_PASSWORD`.

A password needs at least 10^10 estimated guesses (`security.password.min-guesses-log10`),
zxcvbn's level for strong protection against offline attacks on slowly hashed passwords.
The minimum length of 10 follows from that threshold:
zxcvbn estimates a password without any recognised pattern at 10 guesses per character,
so a shorter password can never reach it.
The account's own mail address and names and the words in `security.password.context-words`
count as known words.

The estimate uses zxcvbn4j's own dictionaries
plus the word lists of the zxcvbn-ts language packages.
The build ships every one of them,
generating resources from the npm packages pinned in `gradle/password-dictionaries.versions.toml`
with the plugin in `build-logic`.
A shipped language costs only image size, a loaded one memory.
The languages to load depend on an installation's users (`security.password.dictionary-languages`);
the default, English and German, matches those of a typical installation.
The Arabic, Chinese, Japanese, Persian and Russian lists are mostly romanized,
so they cover passwords typed in those scripts only partially.
SecLists was considered as a source,
but its common password lists derive from the same dataset as zxcvbn-ts's,
without the filtering zxcvbn-ts applies.

The check runs only on the server.
Clients get the result through the `userPasswordStrength` query,
to show the strength while a password is typed.
Running zxcvbn-ts in the web client instead was considered and rejected:
its estimate differs from zxcvbn4j's and it can only ship a fraction of the dictionaries,
so the client would accept passwords the server rejects,
and even reduced dictionaries cost about half a megabyte of download.

The query's hint is zxcvbn's own feedback.
zxcvbn only gives feedback about a single match and has no messages for some common cases,
such as several common words combined,
so the hints are not always specific.
Deriving our own diagnosis from the matches with our own messages would close that gap,
but was not considered worth the effort for now.

Passing the check means that a password resists guessing as zxcvbn models it,
not that it is safe in every respect.
The estimate counts the guesses of an attacker who tries common passwords,
dictionary words and patterns in order of likelihood.
It says nothing about phishing, social engineering, malware,
or a password reused on another service.
Personal information other than the account's mail address and names,
such as a birthday or a pet's name, is unknown to the check,
so a password built from it can pass.
An account invitation (`verifyUserMailAddressUnauthenticated`) is accepted without a session,
and its link carries no mail address,
so there the query rates a password without the account's mail address and names.
A password built from them can show as sufficient
and is only refused with `WEAK_PASSWORD` when the invitation is accepted;
nothing is stored before that check, so the code stays valid for another attempt.
Passing the user ID and verification code to the query was considered and rejected
as too complex for this case.
Words missing from the loaded dictionaries count as random characters,
which overestimates them.
Passwords are not compared against a database of breached passwords such as Have I Been Pwned;
only the common password lists in the dictionaries cover breached passwords.
A full strength bar in a client therefore means that a password meets this requirement,
not that it is particularly strong.

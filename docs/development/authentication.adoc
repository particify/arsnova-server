All API endpoints, except for the challenge endpoint, require authentication.
In most cases, authentication for an existing user account is needed.
But for a few endpoints, a user account or respective authentication is not available, e.g. login or account creation.
For these cases, anonymous authentication is available, which does not authenticate a specific user.
It instead testifies that the client has solved a proof of work challenge.

== Proof of work

Proof of work is a method where the client has to solve a server provided cryptographic challenge.
While it is easy for the server to generate the challenge and verify the solution, it is expansive to solve for the client.
We use PoW as a form of protection against DoS attacks and bots.

For the implementation of a PoW algorithm the Altcha library is used.
The client fetches a challenge via `GET` request to `/api/challenge` and sends its solution to the URI as `POST` request.
If the challenge is verified successfully, the server responds with an authentication token.
This token has a short expiration time and is only accepted to authenticate a single request.

== Login throttling

`POST /api/auth/login` is rate limited per submitted username.
Attempts are counted before the credentials are checked and discarded again after a successful
login, so only failures accumulate.

Without a limit of our own, how many passwords a client may try is bounded only by the proof of work
challenge in front of the endpoint.
That challenge puts a cost on every attempt, but the resulting rate follows from how quickly the
client solves one, which is a property of its hardware rather than a bound we set.

The exposure is worst against an external directory (see link:ldap.adoc[]),
where repeated failures usually lock the account, but it is not specific to any one provider.

`security.login.attempt-limit`:: Attempts allowed per window, `20` by default.
`security.login.attempt-window`:: Length of the window, `2m` by default.

The counters are held in memory, so the limit applies per instance rather than across a deployment
with several replicas.

== Tokens

JSON Web Tokens are used to authentication clients statelessly for use of the API.
Following a common security practise, two separate tokens are used:

* A short-lived access token which authorizes the client for API access.
  It cannot be revoked.
  The client sends this token in the `Authorization` header for further API requests.
* A long-lived refresh token which allows the client to request new access tokens.
  It can be revoked by increasing the users token version.
  To protect this token against XSS attacks, it is stored using an `HttpOnly` cookie.
  Therefore, it is not accessible through JavaScript.

== Local accounts

A local account authenticates with a username and a password, the username being the mail address
its owner verified.
Creating one is not a single request: the client first obtains a guest account
(`POST /api/auth/guest-account`), then claims it with the `claimUnverifiedUser` mutation, which
parks the address until the code sent to it is submitted.
An account can also be created for someone else, by an administrator through `adminCreateUser` or
by a room's owner through `grantRoomRoleByInvitation` -- both send an invitation and go through the
same service.

Two settings decide what is available:

`security.local-account.enabled`:: Whether local accounts exist at all, `true` by default.
`security.local-account.self-registration-enabled`:: Whether an account can be created by whoever
wants one, `true` by default.
Ignored while local accounts are disabled.

[cols="2,1,1"]
|===
|Path |`enabled: false` |`self-registration-enabled: false`

|`POST /api/auth/login` without a `providerId` |refused |unaffected
|`user-db` entry in `GET /api/configuration` |omitted |unaffected
|`claimUnverifiedUser` |refused |refused
|`grantRoomRoleByInvitation` for an address with no account |refused |refused
|`requestUserPasswordReset`, `resetUserPassword` |refused |unaffected
|`updateUserMailAddress` |refused |unaffected
|`adminCreateUser`, `adminVerifyUserById` |unaffected |unaffected
|===

Three of those paths carry a second check which neither column covers: `claimUnverifiedUser`,
`grantRoomRoleByInvitation` and `updateUserMailAddress` test the address against the allowed
domains below once a request gets past the settings above.
A verification already in flight is unaffected by either setting, since completing one finishes an
account rather than creating it.

Administrative actions are never gated, so an administrator creates and verifies accounts whatever
the settings say.
That is decided from the account acting rather than from the mutation called, which is why the
invitation is refused for a room owner and allowed for an administrator although both reach the
same service method.

A refusal is a domain exception rather than a denied `@PreAuthorize`, because the client cannot
explain the opaque `FORBIDDEN` that GraphQL turns an authorization denial into.

`security.local-account.allowed-mail-address-domains` restricts which addresses an account may be
created for, and is empty by default.
Each entry is a domain in which a `*` label matches exactly one label of the address' domain, so
`*.example.com` covers `mail.example.com` but not `example.com`.
The entries are checked and compiled while the application starts: a pattern which cannot match
locks out everyone it was meant to serve, and reporting that as an error about the submitted
address hides the actual mistake.
Changing one's own address is checked against the list as well, since a restriction one can leave
right after registering is no restriction.
So is an invitation, which would otherwise let a room's owner create the account the restriction
denies its holder -- unless an administrator sends it, administrative account creation being
ungated here as everywhere else.
